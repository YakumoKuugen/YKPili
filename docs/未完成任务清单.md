## P0 · 直接影响可用性

- [x] **【需求】其他接口也各自加访问限制，防止被 B 站封控** 【全局 · 网络】✅ 2026-10-31
  - 诉求：评论接口刚因 `-352` 加过节流，其余接口（首页推荐、搜索、动态、历史、
    消息、私信、收藏、排行、互动写操作、登录）也需要各自的频率上限，
    避免再被风控拦。
  - 根因：之前只有评论区在 App 层做了 1 秒间隔，其他请求共用
    `ReqwestClient` 且**完全不限速**；同时每个需要签名的请求都会重新取一次
    `/x/web-interface/nav`（WBI keys），接口量白白翻倍。
  - 修复：
    - 新增 `yk-core/src/api/limits.rs`：按接口**分组**给最小间隔，真实请求统一在
      `ReqwestClient` 的 `get` / `get_bytes` / `post_form` / `post_json` 里过
      `limits::acquire_for(url, write)`；`auth.rs` 的登录/passport 请求也接了同一套。
    - 分组与间隔（同组第 2 个请求起生效，**第一次不等待**，打开页面 / 起播不变慢）：

      | 分组 | 覆盖接口 | 间隔 |
      |---|---|---|
      | `Comment` | `/x/v2/reply*`（楼中楼响应最大） | 1200ms |
      | `Write` | 点赞 / 投币 / 收藏 / 发动态 / 私信 / 删历史 / 上报进度（全部 POST） | 1200ms |
      | `Nav` | `/x/web-interface/nav`（WBI keys，另有 30 分钟缓存） | 1000ms |
      | `Hotword` | 搜索热搜词 | 1000ms |
      | `Recommend` | 首页 / 推荐流 `feed/rcmd` | 800ms |
      | `Dynamic` | 动态流 / 动态详情 | 800ms |
      | `MsgFeed` | 未读数 / 回复 / @ / 赞 | 700ms |
      | `Session` | 私信会话与消息（`api.vc.bilibili.com`） | 700ms |
      | `PlayUrl` | 取流 `x/player/*playurl` | 600ms |
      | `Ranking` / `Fav` | 排行榜 / 收藏夹 | 600ms |
      | `History` / `Search` | 观看历史 / 搜索 | 500ms |
      | `VideoInfo` | 视频详情、`archive/has/like`、`archive/coins` | 400ms |
      | `Danmaku` / `Relation` / `UserCards` | 弹幕 / 关注关系 / 名片 | 400ms |
      | `Suggest` | 搜索联想词 | 300ms |
      | `Other` | 未归类读接口兜底 | 300ms |
      | 全局排队 | 所有真实请求之间 | 80ms |

    - 排队实现：先在锁内把本组的「下一个时间片」推到未来占位，再睡到该格；
      全局 80ms 只在**真正要发**时占位（远期占位不推进全局时间线，
      否则一次 1.2s 后的评论请求会把别的接口全顶到 1.2s 开外）。
    - WBI keys 进程内缓存 30 分钟：`HttpClient` 新增 `cached_wbi_keys` /
      `store_wbi_keys` 两个默认方法（测试替身保持「不缓存」），
      `fetch_wbi_keys` 命中缓存就不再打 `nav`。
    - 已有的局部限制保留：评论区 App 层 1 秒间隔、批量已读 200ms 串行、
      联想词 250ms 防抖。
    - 图床（`i0.hdslb.com` 等）走 GPUI 图片客户端，不属于接口，**不**限流。
  - 验证：
    - 新增单测 8 项：真实 URL 归类、写操作一律进 `Write`、重接口间隔更大、
      首次不等待、同组按间隔排队、全局把不同组排开、旧时间戳不补延迟；
    - 实测（临时 example，已删）：`recommend` 第二次等 740ms、`video_info` 命中
      nav 缓存只用 102ms、`comment` 第二次等 1.2s 且**不拖累**其他分组；
    - `cargo test -p yk-core --lib`（216 项）与 `cargo test -p yk-app --lib`（23 项）全绿。

- [x] **【Bug】评论接口 -352 封控（一次拉太多、连发请求）** 【播放浮窗 · 评论】✅ 2026-10-31
  - 现象：打开视频信息面板的「评论」Tab 直接报
    `评论加载失败：评论接口返回 code=-352：-352`，之后整段评论都出不来。
  - 根因：`COMMENT_PAGE_SIZE = 100` 交给 `fetch_comment_batch` 去拼页，
    而线上 `ps` 上限是 30 —— 「一批 100 条」= **1 秒内连打 4 个**
    `/x/v2/reply/main`；再加上「滚到底就补一页」每帧都判定，连续触发时
    请求密度更高，评论区频控直接把账号/会话打成 `-352`。
    （实测单个请求 `ps=20` 匿名返回 `code=0`、单页响应已 ~270KB，
    所以不是缺 WBI 签名，纯粹是请求量与频率。）
  - 修复：
    - 一次只取 **1 页 20 条**：新增 `api::client::COMMENT_PAGE_SIZE = 20`，
      删除会把多页拼成一批的 `fetch_comment_batch` / `CommentPage::merge`，
      首屏与「加载更多」都只发 1 个请求；剩下的等滚到底再取下一页。
    - 客户端节流：两次评论请求至少间隔 **1 秒**（`COMMENT_REQUEST_INTERVAL`），
      由 `comment_request_wait` / `note_comment_request` 实现；后台线程先等够
      间隔再发，等待期间 `comments_loading_more` 保持为真，不会重复入队。
    - 卡页保护：服务端游标不前进且没有新条目时直接判「到底」，
      避免「滚到底 → 每秒一个无效请求」再次触发频控。
    - `-352` 文案改成人话：「评论请求太频繁，已被 B 站风控拦截（-352），请稍后再试」，
      失败后不自动重试，底部「重试加载更多」由用户手动点。
  - 验证：
    - 新增单测：`comment_page_is_one_request_of_twenty`（一批只发 1 个 `ps=20` 请求）、
      页内 `rpid` 去重、`is_end` 收手、`-352` 文案；
      `comment_requests_are_spaced_at_least_one_second`、
      `comment_batch_is_one_small_request`；
    - `cargo test -p yk-core --lib`（208 项）与 `cargo test -p yk-app --lib`（23 项）全绿，
      `cargo test -p yk-app --no-run` 全部测试目标可编译。

- [x] **【Bug】投币一直返回 400 错误码** 【播放浮窗 · 互动】✅ 2026-10-29
  - 现象：点「投 1 枚 / 投 2 枚」，界面提示 `投币失败：code=-400`（请求错误），
    硬币一枚没投出去。

    而代码只传了 `bvid` —— 服务端拿不到视频 id，直接判 `-400 请求错误`。
    （点赞接口 `archive/like` 认 bvid，所以点赞一直是好的；只有投币挂了。）
  - 修复：
    - `interaction::coin_video` 改成收 `aid`，表单按浏览器的组合发：
      `aid` / `multiply` / `select_like` / `csrf` / `csrf_token`；
    - `aid <= 0` 直接在本地失败并提示，不发无意义的请求；
    - 播放器侧改传 `PlaybackSource.aid`（详情接口带回来的 av 号）；
    - 写操作补上 `Origin` 头（与 `Referer` 同域），和浏览器一致。
  - 顺带加固：读接口 `has/like`、`archive/coins` 改成 **av 号与 bvid 一起带**
    （这两个接口历史上只认其中一个 id 的版本存在，缺哪个都可能回 -400，
    表现是「明明赞过却不高亮」）。缺的那个 id 整段省掉，不发 `aid=0`。
  - 验证：`cargo test --workspace` 全绿；新增单测「缺 aid 直接失败」

- [x] **【Bug】滚轮滚动时封面 hover 动画反复重播** 【首页 / 搜索】✅ 2026-10-29
  - 现象：滚轮滑动列表时，鼠标下方的封面反复缩放；滚回去时已经离开的卡片
    也会重新播一次缩放。
  - 根因：GPUI 的 `on_hover` 在**布局变化、指针不动**时也会重新判定
    （`default_hover_listener_updates_when_layout_changes_under_stationary_mouse`），
    滚动每帧都会给卡片派发 true/false。原逻辑每次 hover 变化都
    `hover_generation += 1`，而动画 id 带着代际号 → 动画从头重播。
    另外虚拟列表滚出视口的卡片会卸载，若 `hovered / leaving` 仍指向它，
    重新挂载时也会按旧状态再播一遍。
  - 修复：
    - 滚轮 / 滚动偏移变化时记录 `last_scroll_at`；
    - `on_hover` 仍然更新 `hovered_card`（指针最后停在哪张卡上不能丢），
      但滚动活跃期内**不推进动画代际**；
    - 渲染层在滚动活跃期把 `hovered / leaving` 当 `false` 传给卡片，
      卡片直接以静态几何绘制，不播缩放；
