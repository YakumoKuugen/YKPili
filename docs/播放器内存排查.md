# 播放器内存排查（内存涨到 2.7 G）

> 现象：挂机播放一段时间后，Activity Monitor 里 ykpili 的占用能到 **2.7 GB**
> （`vmmap` 记录的峰值 footprint 是 **3.2 GB**），关掉播放器又慢慢降回去。
> 结论：不是对象泄漏，是**无界帧队列 + 每帧大块分配抖动**，已修。

## 1. 先确认「是不是真泄漏」

对运行中的进程取三份现场（`<pid>` 换成实际进程号）：

```bash
vmmap -summary <pid>     # 物理占用、分区构成
heap <pid> -sortBySize   # 活跃对象
sample <pid> 3 -file /tmp/s.txt
```

关键读数：

| 指标 | 观测值 | 含义 |
| --- | --- | --- |
| Physical footprint | 420 MB（空闲）/ 885 MB（播放中）/ **峰值 3.2 GB** | 会回落，说明有大量「可回收的空闲大块」 |
| `heap` 活跃对象总量 | **约 130 MB** | 没有对象泄漏，Rust/ObjC 数据都是小头 |
| `Malloc Large (empty)` | 峰值 **791 MB** | 已释放但 malloc 没还给系统的大块 |
| `IOSurface` | 100–130 MB，区域数稳定 | 像素缓冲池没有无限增长 |
| 常驻 `__TEXT`/`__LINKEDIT` | 1.3 GB | 共享库映射，算进 RSS 但不算 footprint |

结论：**活跃数据很小，涨的是「正在排队的帧」和「malloc 保留的空闲页」。**

## 2. 根因一：无界帧队列

`video_worker` 原来是 `mpsc::channel()`（无界）：渲染线程按 60fps 往里塞
`CVPixelBuffer`，UI 线程每 16ms 把队列取空、只留最后一帧。

问题在「取空」发生在 UI 线程：只要 UI 卡一下（切页、解码封面、系统调度、
窗口遮挡判定延迟），渲染线程就会以 **60 帧/秒**继续入队，而每帧数据量是：

| 分辨率 | 一帧 NV12 |
| --- | --- |
| 1080p | ~3.1 MB |
| 4K | ~12.4 MB |

于是 **UI 卡 15 秒 ≈ 2.7 GB**（1080p），和观测到的数字正好一个量级。
队列要等 UI 恢复后才被取空，期间 malloc 已经把这些大块留在 `Malloc Large (empty)` 里，
RSS/footprint 就下不来。

## 3. 根因二：每帧 10.88 MB 的分配抖动

`render_with_format` 每帧把 mpv 的复用缓冲 `clone()` 出来（1080p 8.3 MB），
`rgba_to_nv12` 再新分配 Y/UV 两个 `Vec`（3.1 MB）。60fps 下就是
**约 650 MB/s** 的分配/释放；即使全被回收，malloc 也会保留空闲 region，
这也是 `Malloc Large (empty)` 能到几百 MB 的原因。

## 4. 修复

1. **有界队列**（`video_worker/{macos,windows}.rs`）：
   `mpsc::sync_channel(2)` + `try_send`，UI 没取走就丢本帧。
   内存上限从「UI 卡多久就堆多久」变成「最多两帧」——1080p 约 6 MB、4K 约 24 MB。
2. **借用取帧**（`MpvPlayer::render_frame_ref` / `render_frame_bgra_ref`）：
   返回 `RgbaFrameRef<'_>` 指向 mpv 的复用缓冲，逐帧链路不再复制整帧。
   `render_frame()` 保留原语义（需要自有数据的地方继续用）。
3. **复用 NV12**（`rgba_to_nv12_into`）：渲染线程持有一个 `Nv12Frame` 反复覆写，
   尺寸变化时自动 `resize`。
4. **头像全部走缩略图**（`core::models::face_thumb_url` / `face_thumb_url_at`）：
   卡片署名只有 18pt、评论 28pt、面板 46pt，以前首页卡片、评论、搜索结果、
   账号浮层、顶栏直接拿 B 站图床的**原图**地址——有的头像 2048×2048，
   解码一张就是 16 MB。现在统一换成 `@96w_96h_1c.webp`（账号浮层 176）。
   注意：`mark()`（页面图片驻留）和 `img()` 必须用**同一个** URL，
   否则每帧都会被回收重载；`CoverItem::up_face` 在构造时就换好，两处天然一致。

## 5. 量化验证

`app/crates/infra/examples/mem_probe.rs` 可以直接对比两条热路径：

```bash
cargo run -p yk-infra --example mem_probe -- /tmp/clip.mp4 old 20 1920 1080
cargo run -p yk-infra --example mem_probe -- /tmp/clip.mp4 new 20 1920 1080
```

| 路径 | Rust 每帧分配 |
| --- | --- |
| old（克隆 + 临时 NV12） | **10.88 MB** |
| new（借用 + 复用 NV12） | **0 MB** |

4K 渲染目标跑 15 秒：RSS 稳定在 165 MB（旧路径 205 MB），无增长；
播放中 `vmmap -summary` 的 footprint 稳定在 885 MB 左右，峰值不再随卡顿上冲。

头像缩略图前后（同一台机器、同一个首页、启动 20 秒后）：

| | footprint | peak |
| --- | --- | --- |
| 改前（头像原图） | 412 MB | 741 MB |
| 改后（`@96w_96h`） | **151 MB** | 206 MB |

启动时加载的 100 张图里，改前有 24 张是原图头像；改后全部带 `@…w` 后缀。

## 6. 还没做的

- `nv12_to_pixel_buffer` 仍然每帧 `CVPixelBufferCreate`（约 3 MB/CoreVideo 分配）。
  后续可以换成 `CVPixelBufferPool` 或复用两块 buffer，把这块也抹平；
  现在它是有界的（最多两帧在飞），不再是风险点。
- `remote_image_cache`（`RetainAllImageCache`）只在播放器关闭时整体清空，
  长时间「连着看 + 逛页面」仍会攒评论头像；量级只有几十 MB，暂不处理。
