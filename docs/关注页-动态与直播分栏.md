## 0. 一句话方案

Dock 的二级分页已经是通用机制（`DockTabs` / `DockTab` / `has_secondary`），
关注页只是**多注册一组 tab**：`动态` 沿用现有动态瀑布流，`直播` 新增一个封面网格。
列表数据由 `yk-infra` 新增的 `live` 模块提供；点封面走 `PlayerView::open_live()`
取直播取流地址，交现存 mpv 渲染线程播——**播放器主链路不重写，只加一条「直播源」分支**。
随包 libmpv 已经编进 `flv / live_flv / hls / mpegts` 解复用与 `http/https/tls/crypto`
协议（`packaging/libmpv/features.toml`），直播流不需要重新裁剪库。

## 1. 目标与非目标

### 1.1 目标

| # | 目标 | 判定 |
| --- | --- | --- |
| G1 | 关注页有「动态 / 直播」两个二级分页，交互与排行榜分区胶囊一致 | 点 Dock「正在关注」→ 胶囊浮出；两个 tab 可切换、有 active 态 |

### 1.2 非目标（本次不做）

- **画面内滚动弹幕**：P0 只做右侧列表（12.10.5），不把弹幕画到视频上；「上屏」开关列 P2。
- **醒目留言 / 礼物特效 / 表情图片**：P0 只把 SC、礼物、上舰作为特殊行展示，

- **关注管理**：关注 / 取关、关注列表页不在范围内。
- **纯视频投稿列表**：现有「正在关注」是动态流（视频 / 图文 / 纯文字）。
  本次的「动态」tab 指的就是这条动态流，不是「只筛视频」。

## 2. 现状事实（落地前先对照代码）

### 2.1 Dock 二级分页是一套通用机制，不需要改 shell

| 事实 | 位置 |
| --- | --- |
| `DockTab { index, active, content }`，`DockTabs { open, items, max_width }` | `app/crates/shell/src/dock.rs` |
| `DockItem.has_secondary` 决定箭头槽位常驻；`expandable` / `expanded` 决定箭头方向与槽宽 | 同上 `chevron_slot()` |
| 二级胶囊 `tabs_row()`：active 是磨砂玻璃片，窄窗自动折行 | 同上 |
| 组装点用 `dock_tab_select(index)` 把 tab 序号映射成业务动作 | `app/crates/app/src/lib.rs` |
| 现有两组：消息四通道（`messages_dock_tabs`）、排行榜二十分区（`rank_dock_tabs`） | 同上 |
| `dock_tabs_open` 是**全局共享**开关：进页 / 离页按入口收起 | 同上 `dock_select` 开头 |

结论：**shell 不用改**。只需让 `Route::Following` 也返回一组 `DockTabs`，
并在 `dock_select` / `dock_tab_select` 里加分支。

### 2.2 关注页当前只有一个列表

- 数据：`AppRoot.following: Vec<DynamicItem>` + `following_loading / _loading_more /
  _refreshing / _loaded / _error / _offset / _has_more / _generation`（平铺字段）。
- 视图：`yk_library::following::page()` 接 `FeedState` 画瀑布流，卡片在 `dynamic_card`。
- 入口：`DOCK_ENTRIES[1] = 正在关注`；**已经在关注页时再点一次 = 刷新**。
- 渲染：`content_area()` 里 `kind == Route::Following` 直接调 `following::page()`。
- 刷新：`refresh_page_now()` 的 `Some(Route::Following)` → `load_following_page(false, true)`。
- 重置：`reset_following()`（登录 / 退出都走它）清列表、推进代际。

### 2.3 现有直播视觉资产可以直接复用

| 资产 | 位置 | 复用方式 |
| --- | --- | --- |
| 封面外壳（圆角裁切 / 底部压暗 / 直播角标） | `yk_library::cover::cover_visual()` | `is_live: true, show_stats: false` |
| 「直播中」粉胶囊（`IconName::Radio` + 文字） | `cover::live_badge()`（经 `cover_visual` 暴露） | 不改，直接用 |
| 封面兜底渐变 + 大标题 | `cover::cover_art()` | 封面 URL 为空时自动走渐变 |
| 主播头像点击 | `AppRoot::up_profile_avatar()` → `ensure_up_profile()` | 直播卡的昵称 / 头像复用它 |
| 设计规格（208 宽 / 16:9 / 看过人数文案） | 设计文档 **12.4 直播页 / 12.4.1** | 卡片几何直接对齐 |

### 2.4 播放器现状（决定直播怎么接）

| 事实 | 位置 | 对直播的含义 |
| --- | --- | --- |
| `PlayerView` 全进程单实例；点卡片 → `open_bvid` 取详情 + playurl → `PlaybackSource` | `player/src/controller.rs` | 直播走另一条 `open_live`，共用同一个实例 |
| 渲染线程 `FrameWorker::spawn_with_audio(video, audio, w, h, start)` → `MpvPlayer` → `loadfile` | `player/src/view/playback.rs`、`video_worker/{windows,macos}.rs` | mpv 直接吃 URL，**直播流不需要新增解码路径** |
| `MpvPlayer::new_with_start()` 固定 `http-header-fields: Referer: https://www.bilibili.com/` | `infra/src/media/mod.rs` | **直播必须换成 `https://live.bilibili.com/`**，否则 CDN 403 |
| `keep-open=yes`、`hwdec=auto-copy-safe`、UA 伪装 Chrome | 同上 | 直播沿用，无需改 |
| `PlayerState.duration_secs = 0` 时 `progress()` 返回 0、`time_texts()` 显示 `--:--` | `core/src/player.rs` | 进度条天然失效，但仍占位；直播要显式换形态 |
| `is_playback_finished()` 只在 `duration > 0` 或 eof 时成立 | 同上 | 直播不会因「时长 0」被误判播完；断流由 eof 判定 |
| 播放循环每帧调 `ensure_danmaku_ahead`、每 30s `save_resume_position` | `view/playback.rs` | 直播 `cid = 0`、`resume_key = None`，需要守卫（现有函数有部分兜底，但不能靠运气） |
| `on_playback_finished()` 按设置**自动关闭播放器** | `player/src/controller.rs` | 直播断流绝不能走自动关闭，要改成重连浮层 |
| `panel_tabs()` 固定「评论 / 弹幕 / 选集」 | `view/panel.rs` | 直播改成「弹幕（默认）/ 直播信息」，并复用 400↔200 收起 |
| 控制栏 88px = 弹幕输入 38 + 操作条 50，进度条依赖 `duration` | `view/controls.rs` | 直播要隐藏进度拖动与倍速 |
| `PlaybackSource` 只有点播字段（bvid / aid / cid / 时长 / 续播） | `core/src/playback.rs` | 加 `is_live` / `live_room_id`，其余留空 |
| 随包 libmpv 已启用 `flv / live_flv / hls / mpegts` 与 `http/https/tls/crypto` | `packaging/libmpv/features.toml` | **不需要重编 libmpv** |

## 3. 交互设计

### 3.1 一级入口：箭头与展开态

与「视频排行榜」完全一致：

- `has_secondary = true` 常驻 → 箭头槽位常驻，展开 / 收起时胶囊长度平滑变化。
- `expandable = self.page == Some(Route::Following)` → 停在关注页时箭头才可动。
- `expanded = self.dock_tabs_open`。

### 3.2 二级分页：两个 tab

```text
        ┌──────────────────────────────┐
        │  动态   │  直播 ●             │   ← 二级胶囊（玻璃），active 为磨砂片
        └──────────────────────────────┘
   ┌────────────────────────────────────────────┐
   │ 个性推荐   正在关注 ⌃   视频排行榜            │   ← 一级 Dock
   └────────────────────────────────────────────┘
```

| tab | index | 文案 | 内容 | 角标 |
| --- | --- | --- | --- | --- |
| 动态 | 0 | `动态` | 现有动态瀑布流 | 无 |
| 直播 | 1 | `直播` | 直播封面网格 | 已加载且开播数 > 0 → 6px `bili_pink` 圆点 |

**用圆点不用数字**：数字会随「谁刚下播」快速过期，而 tab 不是实时控件；
圆点只承担「有内容，点进去看」，不承诺精确数量。

### 3.3 行为矩阵

| 当前态 | 动作 | 结果 | 理由 |
| --- | --- | --- | --- |
| 其他页面 | 点「正在关注」 | 切到关注页，停在**上次的分栏**（首次为「动态」）；二级分页**保持收起** | 与视频排行榜一致：进页先看内容，要切分栏再点一次入口展开 |
| 关注页 | 点「正在关注」 | 展开 / 收起二级分页（**不再触发刷新**） | 与消息 / 排行榜统一；刷新有 Dock「刷新」与回顶下拉 |
| 关注页 + 分页展开 | 点「动态」 | 显示动态瀑布流；**回顶**；已加载则不重新请求 | 切 tab 是视图切换，不是刷新 |
| 关注页 + 分页展开 | 点「直播」 | 显示直播网格；未加载或距上次成功 > 60s → 拉第一页；**回顶** | 直播时效性强，但也不能每次切都打接口 |
| 关注页（任一分栏） | Dock「刷新」/ 回顶下拉 | **只刷新当前分栏** | 另一个分栏没在看，刷它是浪费 |
| 关注页 | 离开到其他页 | 收起分页；两个分栏的列表保留（会话内） | 回来不该重新等一次网络 |
| 未登录 | 进入关注页 | 弹登录；两个分栏都画登录卡 | 与现状一致 |
| 直播分栏 | **点封面** | 打开播放浮窗，**直接播放直播流**（复用封面入场动画） | 需求明确要求「播取流直播内容」 |
| 直播分栏 | 点主播头像 / 昵称 | 打开 UP 主空间浮窗（`ensure_up_profile`） | 复用现有能力 |
| 播放器内（直播源） | 关闭浮窗 | 停止播放、释放 mpv，不上报历史 | 直播没有历史条目 |
| 播放器内（直播源） | 断流 / 下播 | 「直播已结束或连接中断」浮层 + 「重新连接」/「关闭」 | 绝不自动关窗 |

> 与排行榜保持一致：**进页不自动展开**分区胶囊，只有「已经在关注页」时
> 再点一次入口才展开 / 收起。分栏状态仍然记忆（离开前停在直播，回来还是直播），
> 但不替用户把胶囊弹出来。

### 3.4 播放器里的直播交互

| 控件 | 直播行为 | 理由 |
| --- | --- | --- |
| 播放 / 暂停 | 可用；暂停后 mpv 继续缓存，恢复继续播 | 用户可能只是走开；恢复后不做 seek（直播 seek 不可靠） |
| 进度条 | **不渲染拖动轨道**，换成 `LIVE` 粉胶囊 + 已看时长 `mm:ss` | 直播没有总长，拖动没有意义 |
| 时间码 | 左：已看时长；右：不显示（或 `LIVE`） | 同上 |
| 倍速 | 隐藏 | 倍速会持续累积延迟，直播场景没有意义 |
| 画质 | 可用：原画 / 蓝光 / 超清 / 高清 / 流畅（来自 `g_qn_desc`） | 复用视频画质菜单的换流代际 |
| 音量 / 静音 / 全屏 | 可用 | 与点播一致 |
| 弹幕输入 | 可用：控制栏 38px 行发送直播弹幕 | 与官方聊天框同一个发言链路；未登录点击去登录 |
| 弹幕层 | 不画在画面上，集中到右侧「弹幕」面板（12.10.5 对应的实现见 6.8） | 遮脸与性能成本高；列表化更稳 |
| 信息面板 | Tab：**弹幕（默认）** / 直播信息（主播、分区、房间号、关注） | 直播间的聊天是主内容，信息是次级 |
| 面板收起 | 与点播同一套：默认 200，hover 唤出 400 / 移出 220ms 收回 / 骑边界按钮常驻 | 不另造一套交互；控制栏宽度与视频区一致，**不随面板变化** |
| 点赞 / 投币 / 收藏 | 隐藏 | 这些是投稿互动接口，对直播无效 |
| 选集 / 分 P | 隐藏（`panel_tabs` 不再出现） | 直播没有分 P |
| Esc 两次关闭 | 保留 | 与点播一致 |

### 3.5 滚动与状态保留

| 项 | 规则 |
| --- | --- |
| 切 tab | 内容区回顶（`scroll_content_to_top()`） |
| 切回已有分栏 | 不重拉、不重建列表；滚动位置**不记忆**（回到顶部） |
| 直播分栏加载更多 | 底部居中胶囊按钮「加载更多 / 正在加载…」，与动态流一致 |
| 触底自动加载 | P0 不做：关注量通常 < 100；P2 再评估 |
| 刷新胶囊 | `following_refreshing || following_live.refreshing` 时显示「正在刷新当前页面…」 |
| 播放器打开时 | 内容区照常被播放器覆盖（现有 `behind_player` 逻辑不变） |

### 3.6 键盘与焦点（P2）

关注页目前没有专门的键盘导航；分栏 tab 随「Dock 键盘化」一起做。
播放器里的直播控制沿用点播的键位（空格暂停、F 全屏、Esc 关闭），
禁用项（左右方向键 seek、倍速快捷键）在直播下 no-op。

## 4. 视觉规格

### 4.1 直播网格几何

直接复用首页网格的列宽算法 `yk_library::home::card_metrics(available)`，
**不写第二套**：

| 项 | 值 | 令牌 |
| --- | --- | --- |
| 内容区可用宽 | 视口宽 − 48 | `SPACE_6 * 2` |
| 列数 | `floor((available + 16) / (208 + 16))`，最少 1 列 | `COVER_CELL_WIDTH`、`SPACE_4` |
| 卡片宽 | 均分可用宽（减列间距），最小 208 | `COVER_CELL_WIDTH` |
| 卡片高 | 184（封面 108 + 标题 2 行 + 主播行） | `COVER_CELL_HEIGHT` |
| 行 / 列间距 | 16 | `SPACE_4` |
| 卡内边距 | 8 | `SPACE_2` |
| 封面 | 宽 = 卡宽 − 16，比例 16:9（192×108 @ 208 卡） | `COVER_ITEM_WIDTH/HEIGHT`、`MEDIA_RADIUS` |
| 底部预留 | 96 | `DOCK_RESERVED` |

可见范围裁剪沿用动态流同一套思路：用 `visible_y` 算出可视行区间
（`row_h = 184 + 16`），**只构建可视行 ± 1 行**，其余用等高占位块。
不要给全部卡片建真实元素——动态流已经踩过「每张卡注册一串监听器，
滚两页后鼠标一动就卡」的坑（`following.rs` 内注释）。

### 4.2 单卡解剖

```text
┌──────────────────────────────┐
│ ┌──────────────────────────┐ │
│ │ 直播中            3.0万看过│ │  ← 左上粉胶囊 / 左下人数胶囊（压在压暗层上）
│ │                          │ │
│ │        封面 16:9          │ │
│ │                          │ │
│ └──────────────────────────┘ │  ← rounded 12，hover 放大 1.04
│ 今天也在认真打排位            │  ← 13px / 2 行 / line_clamp(2)
│ ●  生肉烹饪师  ·  英雄联盟     │  ← 头像 18 + 昵称 + 分区名，单行
└──────────────────────────────┘
```

### 5.2 列表接口：首选 + 备选（**必须实测确认**）

「关注的直播列表」不是现有接口，落地第一步是**探针**，不是写代码。

**候选 A（首选，一次请求）**

```text
GET https://api.live.bilibili.com/relation/v1/feed/feed_list?page=1&page_size=30
Cookie: SESSDATA=...; bili_jct=...; DedeUserID=...
Referer: https://live.bilibili.com/
```

- 预期返回 `data.list[]`：`roomid` / `uid` / `uname` / `face` / `title` / `cover` /
  `watched_show{num,text_small,text_large}` / `online` / `area_v2_name` 等。
- 预期语义：只包含「关注中且正在直播」的房间。

**候选 B（兜底，两段式）**

```text
GET https://api.bilibili.com/x/relation/followings?vmid={dede_user_id}&pn=1&ps=50&order=desc
GET https://api.live.bilibili.com/room/v1/Room/get_status_info_by_uids?uids[]=1&uids[]=2&...
```

- 先拿关注列表（`mid`），再按 50 个一批查直播状态；
- 优点：覆盖「关注了但最近没发动态」的 UP；P2 还能展示「未开播」；
- 代价：请求数 = ceil(关注数 / 50)，需要 24h 关注列表缓存。

**选型规则**：A 可用 → 用 A；A 被风控 / 下线 → 切 B，只改
`fetch_following_lives` 内部，视图层无感。

**核验清单（落地前一次性做完，结论回填本文）**

| # | 步骤 | 记录 |
| --- | --- | --- |
| 1 | 带真实 Cookie 打候选 A（`page_size=5`） | HTTP 状态、`code`、`message`、`data` 键名 |
| 2 | 保存一份脱敏响应做单测 fixture | 字段名以真实响应为准，不按文档硬编码 |
| 3 | 断网 / 无 Cookie / Cookie 过期各打一次 | 错误码与文案，回填第 9 节 |
| 4 | 用候选 B 交叉验证 3 位在播 UP | A 是否漏人 / 重复 |
| 5 | 确认 `is_ad` / 推荐位是否混入 | 若混入，按 5.3 过滤 |
| 6 | 确认分页语义（`page` 从 1 开始、第二页是否重叠） | 固化 `has_more` 判定 |

### 5.3 列表解析与清洗

1. `code != 0` → `Err("直播接口返回 code={code}（{message}）")`。
2. 文本一律 `format::html_decode` 后 `trim`。
3. 过滤 `live_status != 1`（接口若返回未开播房间）。
4. 过滤 `is_ad == true`，并记日志。
5. 按 `room_id` 去重，保留第一条；`room_id <= 0` 丢弃。
6. 封面 URL 走与 `ranking.rs` 相同的缩略规则。
7. 排序：`watched` 降序（稳定）；全 0 时保持接口原序。
8. `has_more = items.len() >= page_size && 本页新增 > 0`。

### 5.4 直播取流接口与选流规则（**必须实测确认**）

```text
GET https://api.live.bilibili.com/xlive/web-room/v2/index/getRoomPlayInfo
    ?room_id={room_id}
    &protocol=0,1          // 0 = http_stream(FLV)，1 = http_hls
    &format=0,1,2          // 0 = flv，1 = ts，2 = fmp4
    &codec=0               // 0 = avc；先只请求 avc，兼容性最好
    &qn=10000              // 10000 = 原画
    &platform=web
    &ptype=8
    &dolby=5
Cookie: ...
Referer: https://live.bilibili.com/
```

预期返回（字段名以实测为准）：

```text
data.room_info      { room_id, uid, title, live_status, live_start_time, area_name, ... }
data.anchor_info.base_info { uname, face }
data.playurl_info.playurl {
    current_qn, accept_qn[],
    g_qn_desc[]        // { qn, desc } 画质文案表
    stream[] {
        protocol_name  // "http_stream" | "http_hls"
        format[] { format_name, codec[] { codec_name, url_info[] { host, base_url, extra } } }
    }
}
```

**选流规则（P0）**

1. 协议优先级：`http_stream`（FLV）> `http_hls`（HLS）。
   理由：FLV 起播快、延迟低，随包 libmpv 的 `live_flv` 解复用已启用；
   HLS 作为 CDN 不给 FLV 时的回退（`hls` + `crypto` 也已启用）。
2. 编码：只请求 / 优先 `avc`；HEVC / AV1 作为 P2 的可选项
   （libmpv 能解，但部分机器硬解路径不同，先不扩大变量）。
3. 画质：进入时 `qn=10000`；若返回 `current_qn` 低于请求值，以返回值为准，
   画质菜单文案从 `g_qn_desc` 反查。
4. URL 拼接：`host + base_url + extra`（`extra` 已带 `?` 参数时直接拼）。
5. `live_status != 1` → 报「直播已结束」；`playurl_info` 为空 → 报
   「该直播间当前没有可用流（可能需要付费 / 特殊权限）」。

**直播播放模型**

```text

    room_id: i64,
    title: String,
    uid: i64,
    uname: String,
    face: String,
    area_name: String,
```

### 5.5 刷新与缓存策略

| 场景 | 行为 |
| --- | --- |
| 首次切到直播分栏 | 拉第一页（骨架） |
| 再次切回（60s 内） | 直接用内存列表，不发请求 |
| 再次切回（超过 60s） | 保留旧列表静默刷新，失败保留旧数据 |
| Dock「刷新」/ 回顶下拉 | 强制刷新当前分栏（不受 60s 限制） |
| 翻页 | 手动「加载更多」，`page + 1` |
| 退出登录 | `reset_following()` 同时清空直播列表、`loaded = false`、代际 +1 |
| 进程重启 | 不落盘（直播数据时效太短） |

播放地址**不缓存**：每次进入播放器 / 点「重新连接」都重新请求（URL 有有效期）。

### 5.6 为什么不能只靠动态流的作者 mid

动态流只包含「最近发过动态」的 UP；一个只直播、不发动态的主播会完全漏掉。
因此直播分栏必须有独立的关注直播数据源，不能从 `self.following` 里抽
`author.mid` 去批量查状态——覆盖面依赖动态流翻页深度。

### 6.6 错误与重连（P0）

| 情况 | 判断 | 界面 |
| --- | --- | --- |
| 未登录（`-101`） | 取流返回码 | 错误态「登录状态已失效，请重新登录」+ 登录按钮 |
| 房间不存在 / 已下播 | `code != 0` 或 `live_status != 1` | 「直播已结束」+「关闭」 |
| 付费 / 特殊权限 | `playurl_info` 缺失 | 「该直播间需要特殊权限，暂无法播放」 |
| 取流失败（网络） | `Err` | 现有错误态 + 「重试」（重新取流） |
| 播放中断（mpv eof / 错误） | 播放循环 `finished && is_live` | 画面中央浮层「直播已结束或连接中断」+「重新连接」+「关闭」 |
| 连续 2s 无首帧 | 现有 `no_frame_logged` 检测 | 直播下把日志文案改成「直播流无首帧，可能是 CDN / 协议问题」，并在 P1 升级为可视提示 |

> **实测（2026-11-18）· 直播不能信 mpv 的 duration / eof**：直播 FLV 的
> `duration` 只有约 31 秒（CDN 分段元数据），播到那里 `is_playback_finished()`
> 会返回 true，表现为「画面还在播、却弹已结束」。因此直播 worker **不设置**
> EOF 标记，断流统一由播放循环判定：`正在播放 && 窗口可见 && !loading &&
> 连续 8s 没有新帧（Frame 或 Position）`。暂停、窗口不可见、加载中都不算断流。

「重新连接」= 重新 `fetch_live_playback` → 替换 `source.video_url` → 重建 worker
（`tried_worker = false`、`first_frame_seen = false`）。URL 过期也走这条路。

### 6.7 画质切换

- 复用点播的 `quality_generation` 换流代际：菜单点选 → 新代际 → 后台按新 `qn` 拉

### 6.8 直播弹幕面板（右侧聊天框）

**形态**：面板 Tab 是「弹幕（默认）/ 直播信息」；列表只读，输入在控制栏的 38px
弹幕行——单一草稿，面板收起 200px 时输入仍可用。画面内不画滚动弹幕。
面板本身沿用 06 节的收起规则：默认 200、hover 唤出 400、骑边界按钮常驻；
控制栏宽度固定按视频区走，不随面板展开 / 收起变化。

**数据**（新增 `yk_infra::live_chat`）：

- 连接：`wss://broadcastlv.chat.bilibili.com/sub`。用**同步** `tungstenite` + rustls，
  和现有 blocking `reqwest` 同一风格，不引入 async runtime。
- 认证包：JSON `{uid, roomid, protover: 3, platform: "web", type: 2}`；
  心跳 30s；消息包 16 字节头（包长 / 头长 16 / 版本 / 操作码 / 序号），`op = 5` 为业务包。
- 压缩：`protover = 2` 是 zlib（现有 `flate2` 直接解）；`protover = 3` 需实测，
  可能是 brotli——实测不通过就降级请求 `protover: 2`。
- 解析成 `LiveChatMessage { uid, uname, text, kind, color, ts, guard_level, is_admin }`，
  `kind = Danmaku | System | Gift | Guard | SuperChat`；字段名以实测响应为准。
- 发送：`POST https://api.live.bilibili.com/msg/send`
  （`roomid / msg / csrf / rnd / mode=1 / color=16777215 / fontsize=25`），需要登录态。
- 断线：2 / 5 / 10s 退避重连 3 次，之后给「重新连接」；**播放不受影响**。
- 切房间 / 关闭播放器：断开连接、清空缓冲，不跨房间串台。

**状态**：连接中 / 已连接 / 重连中 / 失败 / 未登录（只读）/ 发送中 /
发送失败（可重试）/ 被禁言。

**实测限流（2026-11-18）**：列表 / 取流 / 房间信息 / 弹幕 token 四个接口
**间隔 2s 单独打都是 code=0**；但同一房间的 `getDanmuInfo` 裸请求会稳定回
`-352`，**带 WBI 签名（`w_rid` + `wts`）后 code=0** —— 网页端就是签名的，
这是弹幕连不上的真正原因，不是单纯频率问题。因此落地时：

1. `getDanmuInfo` 必须 WBI 签名，并带 `web_location=444.8`；
2. `api.live.bilibili.com` 整域归到同一个 `Live` 节流桶，间隔 **1s** 串行；
   任何接口命中 `-352` 再把整域冷却 **10s**；
3. `getDanmuInfo` 的 token / host 缓存 **10 分钟**，断线重连直接复用；
   命中 `-352` 时负缓存 60s，并且**不再自动重试 3 次**，改为面板上「重新连接」；
4. 聊天在取流成功后才连；房间信息只在用户打开「直播信息」Tab 时按需拉。

打开一个直播间 = 1 次取流 + 1 次弹幕 token（缓存命中后 0 次）+
可选的 1 次房间信息，且相邻请求至少隔 1s。批量场景可参考 `bilireq` 的
`get_info_by_id` / `get_status_info_by_uids`（一次传多个房间号 / uid）；
当前单房间播放不需要批量，按需单取即可。发送弹幕按文档口径 `rnd` 用
**Unix 秒**时间戳，并在本地限速 1.5s 一次。

**性能**：环形缓冲 200 条；只渲染可视行；16ms 合帧（短时间内多包只重绘一次）；
面板收起或窗口不可见时停止重绘但继续收包；本地回显与服务端回显按
「uid + 文本 + 时间窗」去重。

**UI 落点**：`PlayerView.live_chat: LiveChatState { messages: VecDeque<LiveChatMessage>,
connection, sending, draft }`；`view/panel.rs` 增弹幕 Tab 的列表渲染，
`view/controls.rs` 的弹幕行接发送。

## 9. 边界与异常

| 情况 | 处理 |
| --- | --- |
| 未登录（列表） | 分栏可见；两个分栏都是登录卡；点「去登录」走 `following_sign_in` |
| 未登录（播放） | 取流 `-101` → 播放器错误态「登录状态已失效」+ 登录入口 |
| 风控（`-352` / `412`） | 列表：「请求过于频繁，请稍后再试」；播放：错误态 + 重试 |
| 关注的主播一个都没开播 | 空态 + 「查看关注动态」按钮 |
| 直播已下播但列表未刷新 | 点进播放器时以 `live_status` 为准 → 「直播已结束」+ 关闭 |
| 付费 / 加密 / 无可用流 | 「该直播间需要特殊权限，暂无法播放」 |
| 直播流地址过期 | 点「重新连接」重拉；P2 才考虑按有效期中途续签 |
| 断流 / CDN 抖断 | 断流浮层 + 重新连接；P1 做 10s 无帧自动重试（最多 3 次，退避 2/5/10s） |
| 播放器里切到别的内容 | 关闭浮窗（现有行为）；直播不写历史 |
| `room_id` 缺失 | 列表阶段丢弃该条 + 日志 |
| 同一房间重复 | 按 `room_id` 去重 |
| 封面为空 / 加载失败 | 渐变兜底 + 标题大字 |
| 昵称 / 标题超长 | `line_clamp(1)` / `line_clamp(2)` |
| 窗口极窄（< 400） | 至少 1 列，卡片撑满可用宽 |
| 弱网起播慢 | 播放器先显示「正在获取播放地址…」；首帧前不弹错误（现有 2s 只记日志） |

## 10. 验收

### 10.1 单元测试（`yk-infra`）

列表：
1. 正常响应 → 字段映射（含 `watched_show` 三种文案）。

4. 再点「正在关注」→ 分页收起，页面内容不变。
5. 未登录：分栏可切，内容为登录卡。
6. 空列表：空态与「查看关注动态」按钮出现，点击回到动态分栏。

### 10.3 起播接线验收（`cargo test -p yk-app --test live_playback`）

1. 注入一条 `LiveRoom`，点封面 → `PlayerView` 实体存在，`source.is_live == true`、
   `live_room_id` 正确（用测试访问器读，不依赖真实网络）。
2. 点主播头像 → 打开 UP 主浮窗，**不**起播。
3. 关闭播放器 → 直播源清空，没有历史上报调用（用测试桩计数）。

### 10.4 真机验收（必须，headless 覆盖不到）

1. 真账号 → 直播分栏 → 有一个在播关注 → 点封面：**1.5s 内出画面、有声音**。
2. 画质菜单：原画 / 高清切换都能重新起播。
3. 全屏、音量、暂停 / 恢复。
4. 断开网络 10s 再连：出现断流浮层 → 「重新连接」恢复。
5. 让主播下播（或挑一个刚下播的房间）→ 「直播已结束」+ 关闭。
6. 关闭浮窗后 CPU / 内存回落（mpv 实例确实销毁）。
7. 弹幕面板：进房即有历史弹幕；新弹幕持续追加；上滚出现「N 条新弹幕」，点击回到底部。
8. 发一条弹幕：立即灰显回显 → 转正常且不重复；断网发送给「重试」。
9. 拔网 10s：弹幕橙点「正在重连」，画面继续播；恢复网络后弹幕继续追加。
7. Windows 与 macOS 各跑一遍（AO 与硬解路径不同）。

### 10.5 视觉截图（`YK_VISUAL=1 cargo test -p yk-app --test pages_visual`）

- `render_following_live`：1280 宽、5 列、8 张卡（长标题 / 短标题 / 无封面各一）；
- `render_following_live_tabs`：分页展开 + active 在「直播」；
- `render_live_player`：直播源下的控制栏（`LIVE` 胶囊、无进度条、无倍速）；
- 仅 macOS / Linux（headless GPU），不进常规 CI。

## 12. 风险与开放问题

### 12.1 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 关注直播列表接口未核实 | 字段 / 路径不符，模型返工 | 先跑 5.2 探针；不行切候选 B |
| 直播取流接口未核实 | 字段结构不同（`stream/format/codec` 嵌套） | 先跑 5.4 探针，脱敏响应做 fixture 再写 model |
| Referer 写死点播域名 | 直播 CDN 403 / 无限转圈 | 6.4 的可配置 Referer 是 P0 必做项，不是优化 |
| 弹幕 WebSocket 协议 / 压缩方式未核实 | 收不到消息或乱码 | 先用 `protover: 2` + zlib；实测通过再试 3；协议失败只影响面板，不影响画面 |
| 弹幕消息洪峰 | 列表重绘拖慢播放 | 环形缓冲 200、只渲染可视行、16ms 合帧；面板收起时只收包不重绘 |
| 断流 / URL 过期 | 画面卡住 | P0 手动重连；P1 自动重试 |
| 高码率原画在弱机掉帧 | 观感差 | 默认原画；掉帧时用户可切低画质（P1 可加自动降档） |
| 打包版 libmpv 协议差异 | 本机能播、装机不能播 | 随包 `features.toml` 已含 flv/hls/http/tls；打包后单独跑一次真机验收 |
| 直播写历史 / 续播 | 观看历史里出现脏数据 | 6.5 守卫；单测断言不调用 |

### 12.2 开放问题

| # | 问题 | 建议 |
| --- | --- | --- |
| Q1 | 直播分栏的 tab 文案是否已定？ | 已定「动态 / 直播」，实现时 `FollowingTab::label()` 硬编码 |
| Q2 | 点封面默认起播，是否还要保留「在浏览器打开」？ | V2 先不做；播放器内可后续加「在浏览器打开」按钮（P2） |
| Q3 | 直播是否显示「已看时长」而非进度？ | 建议显示已看 `mm:ss`，让人知道播了多久；不显示总长 |
| Q4 | 是否需要「回到直播最新」？ | P2；P0 暂停后恢复即追帧，不做 seek |
| Q5 | 进入关注页是否自动展开分页？ | **不自动展开**（与视频排行榜一致，已定）；点入口再展开 |
